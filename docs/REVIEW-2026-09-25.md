# 마이롯지 기획·사이트 점검 및 개선안

점검일: 2026-09-25
방식: 핵심 전제를 질문 → 기획과 구현 근거 대조 → 개선안 → 완료 기준.
대상: 플랫폼 기획서 v0.1, 홍보페이지 개발순서 보고서 v0.1, MyLodge_Business의 현재 화면과 코드.

## 1. 판단 기준과 결론

어제 합의한 작업은 사이트 틀과 GitHub 등록이다. 실제 상담 저장·직원 관리가 없는 것은 그 범위에서는 예정된 미구현이다.
그러나 상담형 1차 공개의 완료 기준에는 미달한다. 화면 틀, 원본 재현, 실제 상담 공개를 별도로 검수해야 한다.

- 화면 틀: 10개 섹션 및 기본 상호작용 존재.
- 원본 재현: 정밀 대조 미완료. 이번 점검에서 Figma 최신 화면을 재대조하지 않았으므로 일치율을 제시하지 않는다.
- 실제 상담 공개: 접수 저장·운영 확인·공개 자료가 미완성.
- 실제 계약·결제·예약·교환·렌트: 후속 범위. 지금의 결함으로 계산하지 않는다.

## 2. 질문으로 드러난 주요 문제

### Q1. 연락처를 남기면 누가 언제 그 내용을 확인하는가?

기획: 플랫폼 기획서 06장 및 개발순서 T4는 실제 저장, 접수 결과, 담당자 목록, 처리 상태를 요구한다.
현재: app.js 54행은 연락처를 남기면 안내하겠다고 설명하지만, 90~100행 제출 처리는 입력 검사와 체험 결과만 표시한다. 저장·전송은 없고 입력은 초기화된다.
판정: 초안으로는 허용되지만 안내 문구가 체험 기능과 충돌한다. 실제 접수가 성공한 것처럼 결과를 표시하는 버그는 확인되지 않았다.
개선: 현재는 버튼과 설명을 '상담 신청 화면 체험'으로 명시한다. 실제 접수 파트에서 저장 성공 후 접수번호와 담당자 확인을 연결한다.
완료 기준: 체험 화면에서 실제 연락을 약속하지 않음. 운영 버전에서는 동일 접수번호를 고객 결과와 직원 목록에서 확인.

### Q2. '확인해 보세요'라고 안내한 권리·비용·운영 주체 자료는 어디에 있는가?

기획: 플랫폼 기획서 05장, 개발순서 T5는 확인된 회사 정보, 상품 상태, 승인 자료와 문의 경로를 요구한다.
현재: 체크리스트는 권리·취소·운영 주체 확인을 권하지만 연결된 자료가 없다. 하단 정책·문의 버튼은 '정식 안내 전입니다' 알림만 표시한다.
판정: 고객의 확인 행동이 끝까지 이어지지 않는다. 문서가 실제로 없는지까지는 확인할 수 없으며 사이트에 연결되지 않은 것은 확인했다.
개선: 확인 주제마다 승인 자료 또는 실제 문의 경로를 연결한다. 자료가 미정이면 확인 담당·준비 상태를 관리하고 내부 시안에서만 표시한다.
완료 기준: 공개 페이지의 각 확인 항목이 유효한 자료 또는 운영 중인 문의 경로로 이어짐.

### Q3. 주문진과 양양 중 무엇을 비교해서 선택하는가?

기획: 05장은 대상과 상태, 공간, 이용 조건, 가격 적용 범위의 설명을 요구한다.
현재: 두 프로젝트는 지역·사진 외에 설명이 동일하고 상세 정보가 없다. 지역 버튼은 상담 관심 지역 선택으로만 연결된다.
개선: 지역별로 승인된 상품 식별명, 현재 상태, 공개 가능한 위치 범위, 공간 정보, 가격 적용 여부, 자료 기준일을 관리한다. 미확정 정보를 임의로 채우지 않는다.
완료 기준: 고객이 두 지역의 확인된 차이를 설명할 수 있음. 아직 비교 가능한 정보가 없으면 '관심 지역' 선택임을 분명히 표시.

### Q4. 19만 8,000원을 낸 뒤 얼마가 남고, '6회'는 무엇을 뜻하는가?

기획: 최초 납입을 제외한 단순 잔액은 3,762,000원이며, 6단계에 최초 5%가 포함되는지는 미정이다.
현재: 총액과 5%는 정확하다. 잔여금 수치가 없으며 '6회 분납 예정'이라고 쓰고 하단에서 포함 여부 미정을 안내한다.
개선: 승인된 적용 상품 기준으로 '총액 396만 원 / 최초 19만 8,000원 / 잔여 376만 2,000원'을 함께 보여준다. 잔여금은 총액에서 최초 납입을 뺀 계산이고 별도 비용을 포함하지 않음을 표시한다. 분납은 '6단계 분납 검토 중 — 최초 납입 포함 여부·금액·시점 미정'으로 정리할 것을 제안한다.
완료 기준: 첫 화면·가격·FAQ·하단 금액을 한 기준에서 변경 가능. 확정되지 않은 회차표를 만들지 않음.

### Q5. 고객이 핵심 설명에 도달하기 전에 왜 이렇게 많이 내려가야 하는가?

관찰: 1280×720에서 이용 장면 3,189px, 공동소유 1,979px, 프로젝트 2,571px. 상세 가격 섹션은 문서 상단 약 8,753px 이후 시작한다. 첫 화면에는 별도 가격 요약과 고정 메뉴의 상담 버튼이 있다.
원인: styles.css의 stack-grid가 PC에서도 1열이다. 대형 사진, 정사각형 120구좌 도식이 페이지 높이를 크게 늘린다.
개선 제안: Figma 재현 기준과 합의한 뒤 PC 사진·프로젝트·설명 영역의 다열 배치, 도식 최대 너비 제한, 제목 줄바꿈을 조정한다. 1280px 화면에서는 제목의 '법.'이 단독 줄로 남는 것도 확인했다.
완료 기준: 승인된 PC·모바일 기준 화면과 대조. 핵심 금액·설명·다음 행동을 쉽게 찾는지 확인.
주의: 이번 개선안은 원본 충실 복사 요구와 충돌할 수 있으므로 임의 반영하지 않는다. Figma 원본에도 동일 문제가 있다면 원본 재현과 UX 개선 중 우선순위를 결정해야 한다.

### Q6. 수집하지 않는 화면에서 왜 개인정보 동의를 필수로 받는가?

현재: 체험 양식이 이름·전화번호·개인정보 동의를 필수로 요구한다. 하단에는 저장·전송하지 않는다고 안내한다. 실제 운영용 보관기간·담당 문의처 등은 아직 제공되지 않는다.
개선: 초안에서는 가상 정보로 체험하도록 안내하고 실제 개인정보를 요구하는 인상을 줄인다. 실제 접수 구현 전에 수집항목·사용 목적·보관·삭제 담당·문의처를 운영 기준으로 확정한다.
완료 기준: 화면에서 설명하는 데이터 처리와 실제 처리가 일치함. 이 검토는 법률 적합성 판정이 아니다.

### Q7. 가격이나 문구가 바뀌면 누가 어디를 수정하는가?

기획: T1·T3는 공통 정보와 변경·승인 방식을 요구한다.
현재: app.js의 긴 문자열 안에 원고·금액·화면이 섞여 있고 index.html의 모바일 하단에도 금액이 별도로 존재한다. 모든 본문이 JavaScript 실행 후 만들어진다.
개선: 상품·금액·FAQ 등 변경 가능한 정보를 별도 데이터로 분리하고, 본문과 동작을 분리한다. 초기에 대형 관리 시스템을 만들기보다 승인 자료와 변경 위치를 명확히 한다. 주요 본문은 초기 HTML에 제공하는 방안을 검토한다.
완료 기준: 공통 값 한 곳 변경으로 관련 화면에 일관되게 반영. 주요 스크립트 오류가 전체 소개 본문 소실로 이어지지 않음.

## 3. 유지할 요소

- 총 396만 원, 최초 5%=19만 8,000원 계산.
- 120구좌 예시를 실제 계약 실적으로 표시하지 않는 점.
- 모집 완료와 이용 시작을 구분하는 FAQ.
- 콘셉트 이미지 표시, 회원 기능 '준비 중' 표시.
- 확인되지 않은 숙박 일수·수익·관리비 무료 등을 보장하지 않는 점.
- 모바일 고정 상담 버튼과 지역 사전 선택.

## 5. 파트별 개선 순서

아래 기간은 1명이 하루 4~6시간 작업하는 경우의 초기 추정이며 승인·자료 대기는 별도다.

| 순서 | 개선 묶음 | 예상 작업일 | 완료 조건 |
|---|---|---:|---|
| A | 공개 상태·담당·자료·Figma 충돌 기준 결정 | 1~2일 | 내부 시안/상담 공개 구분과 승인 책임 확정 |
| B | 체험 문구 정리, 원본 대조, 합의된 PC·모바일 배치 수정 | 3~5일 | 비교 가능한 기준 화면과 오류 없는 탐색 |
| C | 공통 상품 데이터·원고 구조 정리 | 1~2일 | 가격·FAQ·모바일 표시를 일관되게 변경 |
| D | 실제 상담 저장·직원 목록·상태·실패 처리 | 7~10일 | 시험 접수 한 건의 전체 처리 확인 |
| E | 승인 자료 연결·정책·최종 검수·공개 준비 | 3~5일 | 고객과 운영자 흐름을 실제 환경에서 확인 |

한 파트 확인 후 다음 파트로 진행한다. 파트 D의 도구·로그인·운영 범위가 커지면 재산정한다.
사진·영상 확대, 방문 정원 관리, 모집 수치, 맞춤형 홍보, 계약·예약·교환·렌트는 별도 후속 계획으로 유지한다.

## 6. 사용자에게 먼저 확인할 결정

가장 먼저: Figma와 기획서 또는 사용성이 충돌할 때 무엇을 우선할 것인가?

- 안 A: 원본 복사를 우선하고 기획 보완은 후속 변경으로 분리.
- 안 B(제안): 색상·분위기·구성은 유지하되, 승인받은 문구·배치 개선을 반영.

그다음: 첫 외부 공개가 체험용 소개인지 실제 상담 접수인지, 상담 담당과 승인 자료가 준비됐는지 결정한다.
이번 작업은 점검·개선안 작성이며 사이트 수정·GitHub 반영·공개 배포는 수행하지 않았다.
