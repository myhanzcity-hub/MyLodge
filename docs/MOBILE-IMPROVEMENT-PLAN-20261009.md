## 1. 목표와 우선 결정

모바일 방문자가 별장 분위기, 시설, 오너 혜택, 지역별 파크, 컨시어지를 읽고 선택할 수 있게 한다. PC 화면을 작은 폭으로 축소하는 방식에서 벗어나, 같은 콘텐츠를 모바일의 읽기 순서와 조작 환경에 맞게 배치한다. 기존 카피와 이미지의 의미, 네온 디자인, 치앙마이 외부 연결은 유지하는 것을 기본으로 한다.

먼저 개선할 항목은 이미지 표시 폭과 자원 선택의 불일치, 첫 영상 안의 작은 글자, 실제 강제 다크모드에서의 로고, 확대 시 읽기·조작이다. 이후 태블릿의 긴 카드 흐름과 CSS 규칙 중복을 정리한다. 화면 크기만 통과한 상태를 모바일 개선 완료로 처리하지 않는다.

이 기획은 실행 항목과 검수 기준을 제시한다. 이번 조사로 제품 코드나 운영 배포를 추가 변경하지 않는다. 앞선 검수에서 이미 수정한 항목과 앞으로 작업할 항목은 구분한다.

### 성공 기준

- 320 CSS px 상당 폭에서 일반 본문이 옆으로 밀리지 않고 정보와 기능을 유지한다.
- 큰 글자·행간 변경·한영 전환 후 제목, 안내, 선택 상태와 조작부가 남는다.
- 정한 지원 기기·브라우저의 밝음/다크/확대 상태에서 상단·하단의 MyLodge를 식별하고 주요 카피를 읽을 수 있다.
- 자동 재생을 원할 때 계속 볼 수 있고, 읽기 위해 정지한 상태를 유지할 수 있다.
- 사진은 중요한 시설을 보여주면서 화면에 맞는 해상도를 사용한다.
- 성능은 모바일과 PC를 구분해 측정한다. 로컬 화면 검사 결과를 실제 사용자 성능으로 표현하지 않는다.

## 2. 근거와 현재 상태

### 수집 자료의 적용 원칙

[자료 목록](research/mobile-20261009/SOURCES.md)에 공식 문서 링크와 적용점을 정리했다. WCAG는 목표 접근성 수준의 근거, APG는 인터랙션 설계 참고, MDN은 구현 방식, Google web.dev는 성능 측정·최적화, WebKit/Samsung 문서는 브라우저별 차이의 근거로 사용한다.

성공 기준의 원문은 [WCAG 2.2 Recommendation](https://www.w3.org/TR/WCAG22/)이고, Understanding 문서는 그 해설이다. APG나 인지 접근성 보완 패턴을 그대로 필수 성공 기준으로 취급하지 않는다.

국내 자료로는 [국립전파연구원의 한국형 웹 콘텐츠 접근성 지침 2.2 배포 안내](https://www.rra.go.kr/ko/reference/kcsList_view.do?nb_seq=5247&nb_type=6)를 확인했다. 국내 원문 전체 조항 검독이나 인증 판정은 이번 조사에 포함하지 않았다. WCAG 2.2와 KWCAG 2.2를 같은 번호라는 이유로 동일 문서로 취급하지 않는다.

WCAG의 일반 본문 reflow 기준은 320 CSS px 상당 폭이며, 텍스트 확대는 별도 기준이다. 390px 화면의 가로 넘침이 없더라도 두 기준 전체를 통과했다고 볼 수 없다. [Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), [Resize Text](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html)

고령 사용자에 대한 설계는 글자 크기 외에 명도 대비, 작은 조작의 어려움, 움직임에 따른 집중 방해를 함께 다룬다. 모든 60–70대 사용자가 같은 능력이나 같은 기기를 쓴다는 가정은 하지 않는다. [W3C Older Users](https://www.w3.org/WAI/older-users/)

## 3. 이용자와 핵심 흐름

### 검증할 이용자 상황

1. 카카오 링크로 처음 접속한 60–70대 방문자: 로고와 첫 카피를 읽고 시설로 이동한다.
2. 기본 Android Chrome/Samsung Internet 방문자: 시설 6개를 비교하고 오너 혜택을 읽는다.
3. iPhone Safari 방문자: 첫 영상이 자동 재생되지 않아도 내용을 이해한다.
4. 큰 글자·낮은 시력 사용자의 방문: 확대·간격 변경 후 본문과 정지 버튼에 접근한다.
5. 영문 사용자: 긴 tech community / digital nomads 문구와 서비스 설명을 읽는다.
6. 태블릿·가로 화면 사용자: PC 메뉴로 전환되기 전의 넓고 낮은 화면에서 조작한다.

이 상황은 조사와 테스트를 위한 가설이다. 실제 방문자 비중·기기 비율·읽는 속도가 측정된 사실은 아니다.

### 콘텐츠 순서

첫 영상과 텍스트 대체 → 브랜드 소개 → 시설 6개 → 생활 슬라이드 → 오너 혜택 → 전체 풍경과 지역 파크 → 사진 갤러리 → 미래의 비전과 치앙마이 → 컨시어지 → 마무리와 로고.

현재 순서를 우선 유지하고, 구간마다 제목·사진·핵심 설명·해당 조작 순서로 읽는다. 카드의 문구를 삭제해 짧게 만들거나, 모든 사진을 작은 썸네일로 줄여 세로 길이만 낮추지 않는다. 사용자 요청으로 제거한 각 카드의 페이지 이동 버튼은 복원하지 않는다. 헤더 카테고리와 마이롯지 길잡이의 이동, 치앙마이 이미지 링크는 예외로 유지한다.

제목 계층과 영역 이름도 이 읽기 순서에 맞춘다. 시각적 위치만 바꿔 의미 구조가 뒤섞이지 않게 한다. [W3C Page Structure](https://www.w3.org/WAI/tutorials/page-structure/)

### 내부 상세와 외부 연결의 범위

헤더의 Business Valley는 내부 `business-valley.html` 상세로, 치앙마이 카드 이미지는 `https://hanzcity.com/chiangmai/intro`로 연결된다. 내부 상세는 공통 모바일 스타일·메뉴·로고·한영 확대 검수에 포함한다. 외부 연결은 이미지 한 번 선택, 정확한 목적지, 복귀 동작까지 확인한다. 한즈시티 자체의 모바일 디자인은 마이롯지 코드의 수정 범위와 구분한다. 홈페이지와 상세의 공통 컴포넌트를 수정한 뒤 양쪽을 함께 회귀 검수한다.

## 4. 공통 설계 기준

아래 값은 마이롯지에 제안하는 기본 디자인값이며, 규범 수치와 구분한다. 확대 및 영문에서 컨테이너 높이는 콘텐츠에 맞춰 늘어난다.

| 요소 | 제안값 | 적용 이유 |
|---|---|---|
| 기본 본문 | 17px부터 시안, 최소 기본안 16px | 사진 중심 사이트의 긴 설명과 고령 읽기 검토 |
| 안내·조건 문구 | 14–16px | 중요 정보가 작은 각주로 밀리지 않게 함 |
| 카드 제목 | 24–28px | 본문과 제목 계층 구분, 영문 길이 대응 |
| 구간 제목 | 28–34px, rem 기준 | 모바일 폭과 확대를 모두 고려 |
| 행간 | 본문 1.7–1.85, 제목 1.35–1.5 | 한국어·영문 줄바꿈 평가용 |
| 조작 영역 | 주요 버튼 최소 48×48px 목표 | 손가락 조작 편의. inline 링크는 별도 |
| 조작 간격 | 8px 이상부터 시안 | 인접 버튼 오조작 관찰 |
| 좌우 여백 | 작은 폰 16px, 일반 폰 20px | 카드 폭을 유지하면서 화면 가장자리와 분리 |
| 구간 간 여백 | 40–56px부터 시안 | 기존 큰 PC 여백의 세로 길이 증가 완화 |
| 선택 표시 | 고정 테두리 + 체크/선택 문구 + aria 상태 | 네온 색이나 움직임만으로 상태를 전달하지 않음 |

WCAG 2.2 AA의 target size는 기본 24×24 CSS px와 간격 등의 예외를 포함한다. 위 48px는 프로젝트 사용성 목표다. [Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

텍스트는 일반 4.5:1, 큰 텍스트는 3:1 기준을 적용한다. 큰 텍스트의 기준은 단순히 제목인지 여부가 아니라 크기와 두께로 판정한다. 정보가 되는 버튼 상태·아이콘은 비텍스트 대비도 별도로 검토한다. [Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [Non-text Contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)

### 줄바꿈과 확대

- 제목의 br은 좁은 화면에서도 의미가 이어질 때만 유지한다. 영어 어구 내부를 임의로 고정하지 않는다.
- 본문은 기본 자연 줄바꿈을 사용하고, 긴 어구의 폭 초과만 국소적으로 처리한다.
- 강조 문구는 max-width 및 줄바꿈을 허용한다. 강조 때문에 문장이 잘리면 크기·패딩부터 조정한다.
- 본문 높이·줄 수를 고정하거나 line-clamp로 숨기지 않는다.
- 사용자 간격 변경 시험: 행간 1.5, 문단 뒤 2em, 자간 .12em, 단어 간격 .16em을 동시에 적용해 기능·내용 보존을 확인한다. 이는 기본 디자인의 강제 행간이 아니다. [Text Spacing](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html)

## 5. 화면별 재구성안

### 상단 헤더와 메뉴

기본 헤더는 밝은 로고 받침, 언어 선택, 메뉴 버튼으로 구성한다. 320에서 심볼을 생략하는 현재 방식은 유지하되 워드마크가 식별되는지 확인한다. 로고를 줄여 조작 버튼까지 작게 만드는 방식은 피한다.

메뉴를 열면 현재 구간 표시, 이동 링크, 닫기 버튼을 확인할 수 있어야 한다. Escape·바깥 클릭·목적지 선택으로 닫히며, 단순 닫기에서는 메뉴 버튼으로 초점이 복귀한다. 목적지 선택은 제목 초점 이동을 유지한다. 높이가 낮으면 메뉴 자체가 스크롤돼야 하며 페이지의 선택 영역을 덮고 빠져나오지 못하는 상태는 허용하지 않는다. 고정 헤더의 높이를 측정해 목적지·초점이 보이는 위치를 정한다. [Focus Not Obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html), [Disclosure Navigation](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/examples/disclosure-navigation/)

### 첫 PPT 영상

1. 현재 모바일 MP4·포스터의 실제 선택 경로를 먼저 검사한다. 새로고침, 700px 경계, 가로 회전, 한영 전환을 포함한다.
2. 가장 중요한 첫 카피와 영상의 핵심 내용을 HTML 텍스트로 읽을 수 있게 하는 시안을 우선 만든다. 영상 안 카피와 동시에 겹쳐 두 번 보이는 방식은 피한다.
3. 제안 기본안은 영상 아래 접을 수 있는 동일 카피의 읽기 영역이다. 정지·재생 옆에서 찾을 수 있게 하고, 영역을 펼쳤을 때 자동 전환으로 읽기 위치가 바뀌지 않게 한다. 문구 자체는 수정하지 않는다.
4. 비교안은 자막 없는 모바일 배경 영상 + HTML 카피 레이어다. 이 경우 기존 영상 제작 경로와 동기화 작업이 추가되므로 구현 난도가 높다.
5. 자동 재생 거절 시 포스터·재생 버튼·텍스트가 남는다. 재생 실패를 사이트 전체의 빈 첫 화면으로 만들지 않는다.
6. 30초 무한 반복과 사용자 음량 선택은 유지한다. 강제로 소리를 켜지 않는다.

`playsinline`·muted는 모바일 재생 구현의 근거지만 최신 모든 인앱 브라우저의 자동 재생 보증은 아니다. play Promise 거절과 정책별 대체 상태를 다룬다. [WebKit Video Policies](https://webkit.org/blog/6784/new-video-policies-for-ios/), [Video Performance](https://web.dev/learn/performance/video-performance)

### 시설 탭과 상세

시설 6개는 별장 외관 / 비치사이드 / 풀파티·카바나 / 카페테리아·클럽 / 마켓 / 컨시어지다. 폰에서는 2열×3행을 기본으로 한다. 번호, 고유 아이콘, 이름의 순서를 통일한다. 활성 선택은 움직이지 않는 체크/테두리를 추가해 네온을 모두 동일하게 정지해도 구분 가능하게 한다.

시설을 바꾸면 선택 탭의 초점을 유지한다. 상세 제목·사진·설명은 해당 탭의 패널로 연결한다. 패널 이미지가 늦게 들어와도 탭이 움직이지 않게 비율을 예약한다. 2차원 탭 배치의 시각 순서와 DOM 순서를 맞추고, 키보드는 APG 패턴에 맞춘다. 실제 데이터와 이미지 로드가 느리면 초점 이동만으로 즉시 선택하는 방식보다 Enter/Space 활성화를 검토한다. [Tabs Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/)

### 생활 슬라이드와 사진 갤러리

기본은 자동 무한 반복, 좌우 화살표 없음이다. 모바일에서는 사진 다음 제목·설명·표기를 읽는다. 슬라이드 높이는 가장 긴 장면의 자연 높이를 확보하며, 작은 본문을 큰 고정 박스에 억지로 넣지 않는다.

정지/재생 제어를 DOM에서 장면보다 앞에 두는 안을 우선 검토한다. 화면에서도 구간 시작에 간결하게 배치해 200% 확대 사용자가 긴 본문을 끝까지 스크롤한 뒤에야 정지를 찾는 문제를 줄인다. 제어 문구는 실제 동작을 설명하며, 자동 재생 때 모든 장면을 반복 알림으로 읽어주지 않는다.

[APG Carousel](https://www.w3.org/WAI/ARIA/apg/patterns/carousel/)는 초점 진입·hover 시 정지, 회전 제어, 탐색 제어를 안내한다. 현재 사용자 결정은 hover로 멈추지 않는 자동 재생과 화살표 제거다. 따라서 APG 예제를 그대로 복사하지 않는다. 제안은 **기본 자동 모드 유지 + 정지 버튼 우선 배치 + 동작 줄이기에서 정적 읽기**다. 초점 진입 정지와 정적 전체 장면 읽기는 적용 결정이 필요한 접근성 보완 항목으로 남긴다.

정지 버튼 자체가 있어야 하며 hover 또는 초점에 있는 동안만 잠깐 멈추는 것을 지속 정지의 대체로 쓰지 않는다. [Pause Stop Hide](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide)

### 오너 혜택과 컨시어지

폰에서는 사진·번호·제목·설명 순서의 한 열 카드를 유지한다. 제목 아래 여백과 카드 내부 패딩을 줄여 읽는 흐름을 정리한다. 사진 아래 의미 있는 설명을 접어 감추지 않는다.

태블릿 2열은 비교 시안으로 검증한다. 3개 카드라서 마지막 카드만 크게 늘리지 않고 2열 그리드의 동일 너비로 배치하는 안과 단일 열의 짧은 이미지 안을 비교한다. 200% 글자에서는 카드 최소 폭을 보장하지 못하면 자동으로 한 열로 복귀한다. 768px이라는 숫자만으로 항상 2열을 고정하지 않는다.

가로 휴대폰은 높이가 부족하므로 이미지 비율을 넓게 바꾸는 시안을 먼저 검토한다. 시설·사람이 잘리는 정도를 확인한 후 적용한다. 성능의 sizes와 같은 레이아웃 조건을 사용한다.

### 전체 풍경과 지역 파크

단지 전체 풍경은 전체 구도의 16:9 보존이 기본이다. 주문진·양양 사진은 지역별 구도가 중요한 만큼 임의의 중앙 확대를 하지 않는다. 전경을 너무 작게 줄여 모든 시설이 점처럼 보이는 문제는 ‘핵심 시설을 읽을 수 있는 설명’으로 보완하되 사업 내용을 새로 만들지 않는다.

처음 탭하면 확대되고 두 번째 탭해야 이동하는 동작을 다시 도입하지 않는다. 확대 기능이 필요하면 이동 이미지와 명확히 분리한 조작으로 설계하며, 현재 기획의 기본 범위에는 포함하지 않는다.

### 치앙마이와 미래의 비전

현재 같은 녹색 카드와 밝은 글자 분위기를 유지한다. IT맨/디지털노마드 강조는 선택된 스타일을 유지하되 긴 영문과 200%에서 글자·밑줄·패딩이 잘리지 않게 한다. 이미지 링크는 한즈시티 치앙마이로 한 번에 이동한다. 이미지 대체 텍스트와 링크 이름은 목적지가 무엇인지 설명하고, 탭 가능한 영역과 단순 카피 영역을 혼동시키지 않는다.

### 마무리와 푸터

로고는 밝은 보호 표면 위에 출력하고, 작은 보조 글자를 반투명 색상으로 낮추지 않는다. AI 콘셉트와 실제 시설의 구분 안내는 14px 이상의 본문 계층에서 읽을 수 있게 한다. 푸터 이전의 과도한 빈 공간은 줄이되 문구나 고지 내용을 삭제하지 않는다.

## 6. 이미지 규격과 로딩 계획

이미지 개선은 구도·비율·해상도 선택을 별도로 다룬다. 같은 사진의 큰/작은 파일은 해상도 선택이고, 모바일에 맞춘 다른 crop은 구도 변경이다. srcset/sizes는 실제 이미지 칸의 폭을 알려주고 picture는 필요할 때 구도를 바꾼다. [MDN Responsive Images](https://developer.mozilla.org/en-US/docs/Web/HTML/Guides/Responsive_images)

| 이미지 종류 | 구도 정책 | 기본 비율 제안 | 자원 정책 |
|---|---|---|---|
| 전체 풍경·지역 파크 | 전체 조감도 유지 | 16:9 | 내용 폭 기준 sizes, 모바일/PC 후보 |
| 시설 상세 | 시설 핵심과 사람의 얼굴 보호 | 폰 3:2, 비교안 16:10 | 실제 패널 폭, DPR별 확인 |
| 생활 장면 | 사진 다음 카피 | 16:10 | 과거 1152px 배경 sizes 제거 후보 |
| 서비스 카드 | 행동·서비스 의미가 보이게 | 3:2 또는 가로 전용 비교안 | 가로 844에서도 한 열 폭 반영 |
| 치앙마이·분위기 카드 | 주요 사람·환경이 함께 보이게 | 16:10 | 카드 열 수와 sizes 일치 |
| 로고·네온 아이콘 | 형태 변경 금지 | 원본 비율 | 사진과 다른 품질/색상 기준 |

### 자산별 관리표

각 자산에 파일명, 용도, 원본 폭/높이, 480/960/1680 후보, 파일 용량, 권장 focal point, PC·폰·가로 화면 비율, alt, 콘셉트 표기, 사용 위치를 기록한다. 연계되는 이미지는 같은 자산 사용을 허용하지만 무관한 구간의 중복 사용을 늘리지 않는다. 신규 이미지 생성은 기존 자산으로 안전한 구도를 만들 수 없는 경우에만 별도 작업으로 분리한다.

### 합격 기준

- CSS 표시 폭과 sizes가 같은 열 수·가로/세로 조건을 사용한다.
- DPR 1/2/3 시험에서 흐린 확대 또는 불필요한 가장 큰 파일 선택을 확인한다. 후보 선택은 브라우저·캐시·네트워크에 영향을 받으므로 파일명을 전 기기에서 강제하지 않는다.
- 현재 844 한 열에서 45vw가 적용되는 불일치를 제거한다.
- 이미지의 width/height 또는 aspect-ratio가 로드 전에 공간을 예약한다.
- 화면 밖 lazy 이미지를 미로드 오류로 세지 않는다. 실제 도달 뒤 성공 여부를 검사한다.
- 첫 화면의 중요한 poster/LCP 이미지는 하단 lazy 이미지와 다른 정책으로 관리한다.
- 파일 용량 목표는 화질 비교 후 확정한다. ‘모든 이미지 100KB 이하’ 같은 획일적 규칙을 쓰지 않는다.

## 7. 로고와 밝은 화면 어두운 화면

### 세 가지 상황을 분리한다

1. 사이트가 직접 제공하는 밝은/어두운 테마.
2. OS의 prefers-color-scheme 선호를 브라우저가 전달하는 상황.
3. 브라우저가 사이트 색상·이미지에 강제 변환을 적용하는 상황.

검토실의 어두운 배경이 정상이라고 3번까지 완료한 것으로 기록하지 않는다. `color-scheme`은 지원 색 체계를 알리는 구현 수단이고, `prefers-color-scheme`은 사용자 선호 감지다. 전 기기의 이미지 색 변환 방지 보증은 아니다. [MDN color-scheme](https://developer.mozilla.org/en-US/docs/Web/CSS/color-scheme), [MDN prefers-color-scheme](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-color-scheme)

Samsung 공식 2020 문서는 강제 변환과 작은 이미지/로고 분류의 한계를 설명한다. 이 자료는 문제의 원리를 설명하는 참고이며, 2026년 설치 버전의 설정 위치나 완전한 해결책을 확정하는 근거로 사용하지 않는다. [Samsung Dark Mode](https://developer.samsung.com/browser/blog/en/2020/12/15/dark-mode-in-samsung-internet)

### 로고 구현안

기본안은 현재 투명 로고 + 밝은 보호 표면 + 원본 비율 + filter none/normal blend다. 상단은 crop용 컨테이너와 실제 이미지 크기를 함께 검수한다. 하단은 원본 워드마크·심볼이 전부 보이는 상태를 기준으로 한다.

실기기 강제 변환에서 보호 표면이 바뀌거나 로고가 여전히 회색으로 보이면, 밝은 배경을 자산 자체에 포함한 별도 로고 표면과 원본 투명안의 비교 시험을 한다. 자산을 평면화하면 항상 해결된다고 가정하지 않는다. 브랜드 색·여백·선명도가 좋아지는지 실제 캡처로 결정한다. 로고를 CSS로 역반전해 다른 기기에서 잘못 출력되는 수정은 피한다.

### 로고 합격 기준

- 상단과 하단에서 MyLodge 및 한글 워드마크가 식별된다.
- 밝은/어두운 모드에서 회색 사각형, 검은 반전, 흰색 덩어리, 부분 잘림이 없다.
- 이미지가 늦거나 실패해도 접근 가능한 링크/브랜드 이름이 남는다.
- 헤더 로고를 누르는 영역에 초점 표시가 있으며 같은 기능의 홈 이동이 가능하다.
- CSS 계산색만 기록하지 않고 실제 렌더링 캡처를 함께 저장한다.

## 8. 동작과 상태 관리

사용자 기본 모드에서는 요청된 자동 무한 재생과 눈에 띄는 네온을 유지한다. 동작 줄이기 선호가 있으면 자동 전환·네온 이동·큰 카메라 이동을 정적으로 대체한다. 한 효과를 꺼도 다른 효과가 계속 움직이는 부분 제어를 피한다. [MDN Reduced Motion](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion)

| 상태 또는 입력 | 제안 동작 | 검수 내용 |
|---|---|---|
| 첫 진입 | 허용된 무음 영상/자동 슬라이드 | 실패하면 poster·읽기 내용·재생 조작 |
| 사용자가 정지 | 해당 동작을 지속 정지 | 메뉴·회전·구간 이동 뒤 임의 재시작 없음 |
| 화면 밖 | 해당 애니메이션/타이머 정지 | 다시 보일 때 중복 타이머 없음 |
| 메뉴 열림 | 배경 영상·슬라이드의 일시 중단 비교 | 닫은 뒤 사용자 정지와 자동 일시 중단을 구분 |
| 탭 비활성 | 작업 중단 | 복귀 시 사용자의 정지 의도 유지 |
| 동작 줄이기 켜짐 | 정적 표시 | 모든 모션 종류 적용 |
| 동작 줄이기 꺼짐 | 정지 의도를 우선 | 사용자 정지를 자동으로 해제하지 않음 |
| 정지된 슬라이드 읽기 | 비활성 내용은 초점/읽기에서 제외 | 숨은 장면이 중복 낭독되지 않음 |
| 글자 확대 | 콘텐츠 높이 자연 증가 | 정지/재생 제어가 가려지지 않음 |

현재 비활성 장면을 inert로 제외하는 조치는 유지한다. 정지 상태에서 다른 장면을 읽을 수 있는 접근 가능한 대안은 별도 설계가 필요하다. 기본 화면의 화살표를 복원하지 않는 범위에서, 정적 읽기 보기 또는 의미 있는 선택 제어를 비교한다. 모든 장면의 카피는 기존 문구를 그대로 사용한다.

네온 애니메이션은 선택 표시의 유일한 수단이 아니어야 한다. 색상을 구별하지 못하거나 움직임을 꺼도 선택 상태가 전달돼야 한다. [Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)

## 9. 성능과 초기 로딩

### 측정 목표

실제 사용자 기준의 목표는 모바일/PC별 75백분위에서 LCP 2.5초 이하, INP 200ms 이하, CLS .1 이하다. 현재 사이트가 이 값을 달성했다는 측정 결과는 없다. localhost, 단일 Lighthouse 점수, 정적인 높이 측정은 이 결과를 대체하지 않는다. [Web Vitals](https://web.dev/articles/vitals)

### 초기 로드 개선 순서

1. 첫 콘텐츠의 실제 LCP 요소를 확인한다. poster인지 영상 첫 프레임인지 텍스트인지 측정한다.
2. HTML에서 핵심 정보를 발견하는 시점과 JS 교체 후 표시되는 시점을 비교한다.
3. 여러 구성 스크립트에서 같은 DOM과 이미지를 다시 만드는 비용을 조사한다. 실제 defer 순서는 app→cinematic→chairman→scenery→mobile→intro→branding→editorial→localization→mobile-layout이다. 선언 순서와 이후 이벤트 변경을 함께 기록한다.
4. 필요하면 승인된 제목/첫 읽기 내용/로고를 초기 HTML에 넣고, JS는 기능을 붙인다. 사업 조건을 초기 문구로 새로 확정하지 않는다.
5. 우선 다운로드 자원과 하단 lazy 자원을 나누며, 모든 사진에 high priority를 붙이지 않는다.

핵심 자원 발견 지연과 표시 지연은 서로 다른 원인이다. 첫 화면을 JS로 만드는 현재 구조는 측정 후보이며, 실제 병목이라고 단정하지 않는다. [Optimize LCP](https://web.dev/articles/optimize-lcp)

### 전송량과 움직임

첫 모바일 영상은 현재 파일 크기 약 2.36MB인 한국어 자산을 사용한다. 파일 크기가 실제 전송량·시작 시간·배터리 사용을 곧바로 의미하지 않는다. 한영 및 회전 시 두 영상을 모두 받는지 확인한다. preload는 브라우저 힌트이므로 값을 바꾸는 것만으로 결과를 보장하지 않는다.

이미지·영상·폰트의 로드 공간을 예약하고, 페이지 첫 구성 및 언어 교체에서 위아래 위치가 바뀌는지 측정한다. 생활 슬라이드의 높이 안정화는 일부 구간의 보완이며 페이지 전체 CLS 적합 판정은 아니다. [Optimize CLS](https://web.dev/articles/optimize-cls)

시설 탭, 메뉴, 언어 선택은 실제 입력과 다음 화면 표시를 함께 측정한다. 많은 DOM 교체, 이미지 디코딩, 동시에 움직이는 테두리의 페인트가 조작을 막는지 조사한다. [Optimize INP](https://web.dev/articles/optimize-inp)

### 실험 조건

동일 기기에서 cold/warm cache, 일반/제한 네트워크, 첫 페이지/중간 hash 직접 접근을 구분한다. 모바일 기기의 모델·OS·브라우저 버전·연결·날짜를 기록한다. 수치가 없으면 미측정으로 적고, 추정 점수를 작성하지 않는다. 성능 데이터 수집 서비스를 외부에 연결하는 작업은 별도 범위다.

## 13. 사용자 관찰 기획

실제 참여자를 대상으로 향후 시행할 제안이다. 이번 세션에서 이용자 조사나 60–70대 사용성 시험을 실시한 것은 아니다.

### 모집과 진행

초기에는 60–70대 3명 이상과 다른 연령/영문 이용자 2명 이상을 포함하는 소규모 관찰을 제안한다. 이는 통계적 대표 표본이나 ‘5명이면 모든 문제를 찾는다’는 주장이 아니다. 평소 사용하는 휴대폰·브라우저·글자 크기와 안경 착용 등 실제 읽기 조건을 사용한다. 개인 건강 상태를 불필요하게 수집하지 않는다.

참여 동의를 받고 화면/조작 기록 범위를 설명한다. 진행자가 먼저 버튼 위치를 알려주지 않는다. 1회 약 20–30분은 운영 제안이며 완료 시간을 강제하지 않는다.

| 과제 | 관찰할 질문 | 기록 |
|---|---|---|
| 링크를 열고 첫 메시지 이해 | 무엇을 소개하는 곳인지 자신의 말로 설명 가능한가 | 놓친 문구, 영상 읽기 시간, 확대 행동 |
| 시설 목록에서 비치사이드와 카바나 찾기 | 두 항목이 구별되고 선택 결과를 이해하는가 | 오탭, 상태 인지, 사진/설명 연결 |
| 오너 혜택과 컨시어지 읽기 | 문단을 끝까지 읽고 핵심 차이를 설명하는가 | 글자·대비·문장 줄바꿈·피로 |
| 움직이는 장면 멈추고 읽기 | 정지 조작을 스스로 발견하는가 | 탐색 시간, 포기, 잘못 누른 곳 |
| 치앙마이 이미지로 이동 후 복귀 | 한 번 이동하고 원래 내용을 다시 찾는가 | 링크 인지, 뒤로가기 복구 |
| 가로 회전/다크/글자 확대 | 화면 변화 뒤 계속 읽고 조작하는가 | 로고 인식·잘림·조작 가림 |

결과에는 성공/도움 필요/실패, 시도 횟수, 관찰 발언과 원인을 기록한다. 늦게 읽는 것을 개인 실패로 분류하지 않는다. 동일 원인이 여러 과제에서 나타나는지 확인하고 설계 변경의 근거로 사용한다. 사용자 관찰과 기준 검수는 함께 필요하다. [W3C Involving Users](https://www.w3.org/WAI/test-evaluate/involving-users/)

## 16. 주요 컴포넌트의 상세 설계 계약

### 읽기 보기

자동 장면과 같은 카피를 제공하는 동일 페이지 내 제어다. 다른 페이지로 보내는 카드 버튼을 복원하는 안이 아니다. 구현 시 새 제어 문구와 표시 위치는 시안에서 확정한다.

- 열기: 현재 장면 번호·사용자 정지 여부·초점을 저장하고 자동 전환을 중단한다.
- 읽기: 모든 장면을 순서대로 제공한다. 숨은 자동 장면과 읽기 장면이 보조기술에 동시에 노출되지 않도록 하나의 활성 읽기 구조를 사용한다.
- 확대: 제목·설명·캡션·조작을 모두 확대할 수 있고, 자연 높이를 허용한다.
- 닫기: 제어 버튼으로 초점을 돌리고 이전 읽기 위치를 복구한다. 닫았다는 이유만으로 사용자 정지를 풀지 않는다.
- 동작 줄이기: 기본 장면을 정적으로 보여주는 것만으로 모든 장면에 접근할 수 있다고 간주하지 않는다. 다른 카피를 읽을 수 있는 경로까지 포함한다.
- 문구/자산: 승인된 카피·관련 사진을 사용한다. 별도 복사본 데이터에서 문구가 갈라지지 않게 한다.

사진을 다시 사용하는 것이 연계된 동일 장면의 읽기 보기라는 점을 기록한다. 무관한 구간에 같은 사진을 새로 넣는 방식은 사용하지 않는다.

### 이미지 규칙의 책임

| 책임 | 단일 기준으로 관리할 값 | 피할 상태 |
|---|---|---|
| 콘텐츠 데이터 | 이미지 용도·alt·후보 파일·연계 여부 | 파일만 교체돼 설명이 이전 사진을 가리킴 |
| 레이아웃 | 열 수·컨테이너 폭·비율·focal point | CSS 한 열인데 sizes는 두 열 |
| 자원 선택 | 레이아웃과 대응한 sizes/srcset | 여러 스크립트가 서로 다른 폭으로 덮어씀 |
| 로딩 | 중요도·lazy·크기 예약 | 아래쪽 사진도 일괄 high priority |
| 검수 | 실제 슬롯 폭·DPR·선택 후보·로드 시점 | 아직 화면 밖인 lazy 자산을 실패로 분류 |

`scenery.js`는 배경 cover에 필요한 폭을 계산하고, `editorial.js`는 사진을 바꾸며, `mobile-layout.js`는 일부 sizes를 다시 덮어쓴다. 정적인 카드 사진과 전체 배경의 폭 정책을 동일한 것으로 취급하지 않는다. 서비스 뒤 배경이 컨테이너보다 넓게 그려지는 현상도 작성자가 의도한 clip인지 확인한 뒤 일반 본문 넘침과 구분한다.

### 대비 측정의 책임

현재 서비스 본문은 rgb(226,233,223), 카드 표면은 rgba(19,62,52,.93)로 관찰됐다. 소개/구상 안내는 사진 배경 위에 놓인다. 이 경우 CSS의 section background 값만 읽어 텍스트 대비를 계산하면 실제 사진·shade·반투명 합성을 놓칠 수 있다.

측정자는 최종 작성자 배경, 부모 투명도, 장식 레이어, 해당 상태를 함께 기록한다. 사진 위 텍스트는 대표 프레임 하나만 보지 않고 밝은 영역과 전환 중 상태를 확인한다. 로고 문제는 별도로 원본 자산과 브라우저 변환을 비교하며, 색 변경을 모두 작성자 CSS 문제라고 단정하지 않는다.

### 지원 환경과 기본 안내

`index.html`에는 JavaScript 이전의 기본 안내와 새로 열기 경로가 이미 있다. ‘기본 HTML이 전혀 없다’고 기술하지 않는다. 다만 시설/주요 소개를 여러 스크립트가 구성하므로, 로드 지연·실패 상태에서 어떤 핵심 내용이 보존되는지는 비교할 필요가 있다. 핵심 HTML을 먼저 제공하고 기능을 덧붙이는 접근을 후보로 삼는다. [Progressive Enhancement](https://www.gov.uk/service-manual/technology/using-progressive-enhancement)

지원 범위는 실제 이용자 기기 근거에 맞춰 갱신한다. GOV.UK의 브라우저 목록이나 이용 비중을 국내 마이롯지의 방문자 통계로 사용하지 않는다. 필요한 내용과 조작이 유지되는지를 비교하되, 사소한 렌더링 차이를 모두 기능 오류로 분류하지 않는다. [Browser/Device Design](https://www.gov.uk/service-manual/technology/designing-for-different-browsers-and-devices)

모바일에서 구간 사이 관계는 제목 계층·여백·같은 카드 형태로 설명한다. 전체 페이지가 길어지면 구조를 명확히 하고, 같은 카피를 반복해서 이해를 보완하는 방식은 피한다. 카피를 유지하면서도 구조로 가독성을 개선할 수 있다. [Clear Page Structure](https://www.w3.org/WAI/WCAG2/supplemental/patterns/o2p03-page-structure/)
