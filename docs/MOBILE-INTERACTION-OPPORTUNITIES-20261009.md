# 마이롯지 모바일 조작 개선안 — 스와이프 이후

작성일: 2026-10-09. 조사 대상: 최신 로컬 개발본과 모바일 검토실. 상태: 조사·기획 문서이며 제품 코드 변경이나 배포를 의미하지 않는다.

## 1. 목적과 판단 기준

사용자가 사진을 좌우로 밀어 즉시 넘기는 기능을 추가한 뒤, 같은 맥락에서 더 편하게 읽고 조작할 수 있는 개선점을 찾는다. 기존 [모바일 개선 기획서](MOBILE-IMPROVEMENT-PLAN-20261009.md)의 화면 배치·이미지 규격 검토를 보완하며, 이번에는 조작 발견성, 재생 중단, 선택 유지, 돌아오기, 확대와 입력 충돌에 집중한다.

- **관찰 확인:** 검토실에서 동작 또는 계산된 스타일을 직접 확인했다.
- **코드 확인:** 관련 처리의 존재·부재를 소스에서 확인했다. 실제 휴대폰 결과까지 확인했다는 뜻은 아니다.
- **설계 제안:** 더 나은 사용 흐름을 위한 후보이며 현재 오류 판정과 구별한다.
- **실기기 대기:** 터치, 핀치줌, 브라우저 뒤로가기 제스처, 운영체제 글자 확대, 화면 읽기 등 휴대폰에서 확인할 항목이다.

검토실의 iframe 크기 변경은 기기 회전의 일부 배치 조건을 비교하는 수단이다. 휴대폰의 주소창·소프트 키보드·OS 제스처·실제 터치를 재현하지 않는다. 검토용 200% 글자 확대와 어두운 배경도 OS 확대 및 강제 다크모드와 다르다. 실제 이용자 체류 시간 데이터는 수집하지 않았다.

## 2. 먼저 처리할 다섯 가지

| 순서 | 개선 | 근거 | 기대 결과 |
|---|---|---|---|
| 1 | 사진 갤러리의 확대 허용 CSS 충돌 정리 | 갤러리 계산값은 `pan-y`, 생활 슬라이드는 `pan-y pinch-zoom` | 두 사진 영역의 확대 정책을 일치시킨다 |
| 2 | 좌우 밀기 안내와 사진명 선택 수단 | 현재 숫자·정지 버튼은 있으나 직접 장면 선택 수단이 없다 | 자동 전환을 기다리거나 정밀한 손동작을 하지 않아도 원하는 장면을 읽는다 |
| 3 | 메뉴·초점·읽기 중 재생 중단 정책 통일 | 메뉴를 연 동안 생활 슬라이드가 계속 바뀜. 영상은 메뉴를 반영 | 메뉴와 설명을 읽는 동안 장면이 바뀌는 혼란을 줄인다 |
| 4 | 큰 글자에서도 정지 조작에 즉시 접근 | 320px 영문·검토용200%에서 정지 버튼 y1094px, 화면높이568px | 읽는 도중 바뀌는 내용을 쉽게 멈춘다 |
| 5 | 언어·뒤로가기·가로 전환에서 선택과 읽기 위치 유지 | 실제 언어 메뉴에서 선택 초기화, 실제 뒤로가기에서 섹션 시작으로 복귀 | 번역이나 다른 구간 확인 뒤 보던 내용을 이어 본다 |

기존에 사용자가 제거한 좌우 화살표를 다시 넣는 것을 전제로 하지 않는다. 장면 이름을 고르는 간단한 선택 UI, 또는 현재 페이지 안에서 읽는 정적 보기 등을 비교한다. 기존 카피와 승인된 이미지도 이 조사만으로 변경하지 않는다.

## 3. 현재 잘 동작하는 부분

1. 갤러리를 수동 정지한 뒤 54초 동안 장면이 유지됐다. 수동 정지를 자동으로 해제하지 않는 성질을 유지한다.
2. 메뉴와 언어 선택은 동시에 열리지 않는다. 겹치는 패널 문제로 잘못 분류하지 않는다.
3. 스와이프 코드는 버튼·링크 입력을 제외하고, 세로 이동·다중 터치·취소·캡처 손실을 별도로 처리한다.
4. 비활성 사진과 생활 장면에는 `aria-hidden`과 `inert`를 적용한다. 자동 전환 상태 문구는 `aria-live="off"`다.
5. 문서가 숨겨지거나 동작 줄이기 설정을 사용하면 자동 전환을 중단하는 처리가 있다.
6. 390px에서 언어 버튼 44×44px, 메뉴 버튼 약 44×50px, 갤러리 정지 버튼 최소 높이 44px를 확인했다. 이 버튼들을 일괄적으로 너무 작다고 판정하지 않는다.
7. 수동 정지한 갤러리는1440·768·390px로 바꾸고 각각14초 관찰해도 같은03/03 장면과 정지를 유지했다.
8. 낮은844×260px 화면에서는 마지막 메뉴 항목에 초점을 두면 내부 스크롤이 따라가며 항목을 보여줬다.

## 4. 개선 항목 상세

### A. 사진을 기다리지 않고 원하는 대로 보기

#### I01. 좌우 밀기 기능을 발견할 수 있는 안내 — P1 / 설계 제안

- 현재: 사진은 움직일 수 있지만 화면에는 숫자와 정지 버튼만 보인다. 숫자만으로 좌우 밀기를 알아내기 어렵다.
- 제안: 사진 가까이에 한 번 읽을 수 있는 `좌우로 밀어 사진 보기`를 짧게 표시한다. 반짝임·흔들리는 손·민트색 강조를 기본으로 넣지 않는다. 처음 성공한 조작 뒤 축소하거나 숨기는 비교안도 만든다.
- 기준: 안내를 보기 위해 사진을 가리지 않아야 하고, “사진을 누르면 확대된다”는 오해를 유발하지 않아야 한다. 자동 전환과 수동 밀기 모두 가능하다는 의미를 구분한다.

#### I02. 장면 이름으로 직접 선택하기 — P0 / 코드 확인·설계 제안

- 현재: 생활 슬라이드와 갤러리에 장면 선택 버튼·선택 상자가 없다. 스와이프가 어려우면 다음 사진을 기다려야 한다. 동작 줄이기에서는 다른 장면에 접근하는 수단이 더 중요하다.
- 제안: 갤러리에는 `풀장 / 테라스 / 클럽`, 생활 슬라이드에는 `도착 / 만남 / 밤`처럼 장면명 선택 수단을 비교한다. 실제 표시 문구는 승인된 카피를 사용한다. 작은 점 세 개와 삭제했던 화살표 복원은 기본안으로 삼지 않는다.
- 기준: 한 번 누르면 해당 장면이 나온다. 키보드·음성 입력에도 이름이 전달된다. 수동 정지 상태를 유지하며 사진 선택마다 브라우저 방문 기록을 만들지 않는다.
- 근거: 경로를 따라 움직이는 조작에는 단일 포인터 대안을 검토해야 한다. 현재 방향 판별 방식의 적용 여부는 구현과 실제 조작을 함께 판단한다. [W3C Pointer Gestures](https://www.w3.org/WAI/WCAG22/Understanding/pointer-gestures.html)

#### I03. 사진 두 영역의 확대 정책 일치 — P0 / 관찰 확인

- 현재: 390px에서 생활 슬라이드의 계산된 `touch-action`은 `pan-y pinch-zoom`이지만 갤러리는 `pan-y`다. `styles.css`의 `.benchmark-design .lifestyle-grid.photo-deck`가 모바일 규칙보다 구체적이다.
- 제안: 모바일 규칙의 적용 우선순위를 정리하고 두 영역 모두 세로 스크롤·핀치줌 의도가 전달되게 한다. 조상 요소의 정책도 확인한다.
- 기준: 계산된 스타일 확인 후 실제 Android/iOS에서 두 손가락 확대와 확대 중 이동을 검수한다. `touch-action:none`이나 확대를 막는 viewport 제한으로 스와이프를 해결하지 않는다.
- 근거: 브라우저는 대상과 조상의 `touch-action`을 함께 고려한다. [MDN touch-action](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/touch-action)

#### I04. 화면 가장자리의 브라우저 뒤로가기와 구분 — P1 / 실기기 대기

- 현재: 스와이프 시작점이 화면 가장자리인지 판별하지 않는다. 충돌 발생은 이번 검토실에서 재현하지 않았다.
- 제안: Android/iOS 뒤로가기 제스처가 시작되는 가장자리에서 사진 이동을 우선하지 않는 방식을 비교한다. 회전·확대 상태에 따라 실제 충돌을 먼저 기록한다.
- 기준: 사진을 넘기려다 사이트를 나가는 경우와 뒤로가려다 사진만 바뀌는 경우를 각각 측정한다. 전역 `overscroll-behavior:none` 적용은 피한다. 이 속성은 당겨 새로고침과 브라우저 탐색에도 영향을 줄 수 있다. [MDN overscroll-behavior](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/overscroll-behavior)

#### I05. 세로 스크롤과 느린 대각선 조작 구분 — P1 / 코드 확인·실기기 대기

- 현재: 수평48px 이상, 수평/수직 비율1.4, 세로12px 이후 수직 우세이면 잠금이라는 설계값을 사용한다.
- 제안: 오른손·왼손, 짧은 움직임·느린 움직임·흔들린 움직임을 비교한다. 숫자를 바로 낮추지 말고 오작동과 실패를 함께 기록한다. 회전·글자 확대에서도 CSS 픽셀과 손의 실제 이동량은 같지 않다.
- 기준: 세로로 내려 읽다가 장면이 바뀌지 않고, 의도한 좌우 밀기는 과도하게 길게 움직이지 않아도 된다. 위 숫자는 접근성 표준이나 사용자 연구 결과가 아니다.

#### I06. 길게 누르기·텍스트 선택·입력 중단 보호 — P1 / 코드 확인

- 현재: 다중 터치·`pointercancel`·캡처 손실·화면 폭 변경은 취소한다. 문서 숨김·페이지 이탈에 대한 제스처 종료 보완, 텍스트 선택 여부 판단은 별도로 없다.
- 제안: 텍스트 선택이나 사진 길게 누르기 중에는 장면 변경을 막고, 앱 전환·전화 알림·페이지 이탈 후 끌기 상태가 남지 않게 한다. 메뉴나 대체 조작 추가 시 제외 대상도 함께 갱신한다.
- 기준: 취소 후 자동 재생은 기존 수동 정지 여부를 존중한다. 사진 저장·텍스트 선택 같은 기본 브라우저 기능을 전역 차단하지 않는다. [MDN Pointer events](https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events), [MDN pointercancel](https://developer.mozilla.org/en-US/docs/Web/API/Element/pointercancel_event)

#### I07. 밀기 입력에 대한 절제된 반응 — P2 / 비교 시안

- 현재: 손을 놓기 전 사진이 따라 움직이는 피드백은 없다. 따라서 사용자는 인식됐는지 마지막 순간에 안다.
- 제안: 작은 이동 반응 또는 현재 장면 번호의 명확한 변화 중에서 비교한다. 전체 화면이 손을 따라 크게 흔들리는 효과는 기본안으로 넣지 않는다.
- 기준: 새 효과가 세로 스크롤·선택·줌·클릭을 방해하지 않는다. 동작 줄이기에서는 이동 애니메이션 대신 즉시 상태를 바꾼다. 단순 스와이프와 요소를 실제로 끌어 이동시키는 기능은 구별하며, 후자로 바꾸면 별도 대체 조작 검토가 필요하다. [W3C Dragging Movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements)

#### I08. 재생 상태와 버튼 위치를 안정적으로 표시 — P0 / 관찰 확인·설계 제안

- 현재: 320px 영문 긴 캡션에서 조작 줄이 한국어보다 높아졌다. 생활 슬라이드 글자200%에서는 정지 버튼이 화면 밖에 놓였다.
- 실제 페이지 추가 확인: 390px 영문 캡션은2줄로 유지돼 정지 버튼이 안정적이었다.320px에서는 캡션2↔3줄 변경에 따라 버튼 y410.8↔422.3px로 약11.5px 이동했다. 조건별 결과를 분리한다.
- 제안: `자동 재생 중 / 정지됨` 상태를 명확히 하며, 캡션 길이에 따라 정지 버튼이 흔들리지 않는 배치를 비교한다. 긴 생활 장면은 읽기 시작 부분에도 정지 수단이 보여야 한다. 타이머를 강하게 점멸시키거나 읽기 압박을 주는 큰 카운트다운은 피한다.
- 기준: 320px·영문·글자 확대·가로 화면에서 장면을 읽으며 정지 기능에 접근할 수 있다. 화면 고정 버튼을 추가한다면 본문·초점·사진을 가리지 않는지 함께 검수한다.

### B. 읽는 동안 바뀌지 않게 하기

#### I09. 메뉴와 조작 초점이 있을 때 재생 중단 — P0 / 관찰 확인

- 현재: 메뉴를 열어도 생활 슬라이드가 01→02→03→01로 바뀌었다. 갤러리 정지 버튼에 초점만 둔 경우에도 장면이 바뀐다. 첫 영상은 메뉴 열림을 반영하는 처리가 있다.
- 추가 확인: 실제 첫 영상은 메뉴가 열리면 같은 시점에 멈춘다. 언어 패널을 열면 메뉴는 닫히고 영상이 다시 재생됐다. 패널 종류에 따라 중단 규칙이 다르다.
- 제안: 영상·생활·갤러리의 중단 이유를 통일한다. 메뉴·언어 패널·장면 선택·키보드 초점이 읽기를 요구하는 동안 해당 재생을 중단한다. 초점 진입으로 멈춘 경우 자동 재개 여부는 명시적인 재생 선택을 기준으로 정한다.
- 기준: 메뉴 읽기 중 뒤에서 장면이 바뀌지 않는다. 메뉴를 닫는 것과 사용자가 수동 정지를 해제하는 것을 혼동하지 않는다.
- 근거: APG 캐러셀은 초점 진입 시 정지하고 사용자가 회전을 다시 시작하도록 제안한다. 이는 참조 패턴이며 사이트 전체의 WCAG 인증 판정은 아니다. [W3C APG Carousel](https://www.w3.org/WAI/ARIA/apg/patterns/carousel/)

#### I10. 실제 읽기 영역의 노출을 기준으로 재생 — P1 / 코드 확인

- 현재: 관찰기의 `threshold:.25`를 지정했지만 재생 여부에는 `isIntersecting`만 사용한다. 아주 일부가 보이는 첫 교차에서도 true가 될 수 있다.
- 제안: 사진·설명·조작부 중 읽기와 관련된 영역의 노출을 기준으로 한다. 전체 영역25%를 무조건 만족시키는 단순 변경은 피한다. 확대된 장면이 화면보다 길면 그 기준 자체가 부적절할 수 있다.
- 기준: 하단 일부만 보이는데 읽기 시간이 소비되지 않는다. 메뉴와 고정 헤더가 가린 상태도 별도로 고려한다. [MDN IntersectionObserver](https://developer.mozilla.org/en-US/docs/Web/API/IntersectionObserver/IntersectionObserver), [MDN isIntersecting](https://developer.mozilla.org/en-US/docs/Web/API/IntersectionObserverEntry/isIntersecting)

#### I11. 돌아왔을 때 바로 넘어가지 않는 시간 정책 — P1 / 설계 제안

- 현재: 타이머를 중단하고 새로 예약한다. 수동 밀기 후에는 현재 장면의 읽기 시간을 새로 부여한다. 설계시간은 생활 기본14초·최대22초, 갤러리 기본10초·최대16초다.
- 제안: 메뉴 닫기·백그라운드 복귀·언어 전환·이미지 로드 후에는 처음 보게 된 현재 내용을 읽을 수 있는 여유를 준다. 단순 탭과 취소도 시간을 다시 시작하므로 의도에 맞는지 실제 사용 흐름으로 비교한다.
- 기준: 앱에서 돌아오자마자 장면이 넘어가지 않는다. 수동 정지 상태는 유지한다. 이미지가 준비되지 않은 시간을 읽기 시간으로 계산하지 않는다. 이는 향후 정책이며 실제 체류 데이터로 검증된 값이 아니다.

#### I12. 수동 선택만 간단히 알려주기 — P1 / 설계 제안

- 현재: 자동 전환 카운터는 `aria-live="off"`라 매번 읽지 않는다. 수동 밀기 결과를 별도로 알려주는 상태 영역은 없다.
- 추가 확인: 실제 영문 화면에서 영역 이름은 영어지만 `aria-roledescription`은 `캐러셀/슬라이드`로 남아 있다. 조작 결과 안내와 함께 역할 설명도 현지 언어로 일치시킨다.
- 제안: 직접 장면을 선택했을 때만 `2 / 3, 테라스`처럼 짧게 알린다. 자동 전환 때 반복해서 본문을 낭독하지 않는다.
- 기준: VoiceOver·TalkBack에서 사진명과 번호를 한 번에 이해하고, 포커스가 뜻하지 않게 이동하지 않는다. 사진 선택 UI 자체의 이름·현재 상태가 충분하면 추가 알림을 중복시키지 않는다. [W3C Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)

#### I13. 정지 버튼의 이름과 역할 정리 — P1 / 코드 확인

- 현재: `aria-pressed`를 바꾸면서 표시 이름도 `자동 재생 멈추기 ↔ 자동 재생 시작하기`로 바꾼다. 검토실 접근성 트리에서는 체크박스 형태로 전달됐다. 실제 휴대폰 낭독은 미검수다.
- 제안: 바뀌는 동작 이름의 일반 버튼 또는 고정된 이름의 토글 버튼 중 하나를 일관되게 사용한다. 화면 문구와 접근성 이름도 맞춘다.
- 기준: 현재 상태와 눌렀을 때의 동작을 혼동하지 않는다. 한·영 모두 일관된 역할을 전달한다. [W3C APG Carousel](https://www.w3.org/WAI/ARIA/apg/patterns/carousel/), [W3C Label in Name](https://www.w3.org/WAI/WCAG22/Understanding/label-in-name.html)

#### I14. 모든 장면을 천천히 읽는 선택지 — P1 / 비교 시안

- 현재: 동작 줄이기는 자동 전환을 멈추지만 현재 장면 이외 접근을 보장하는 선택 UI는 없다.
- 제안: 현재 페이지 안에서 같은 사진과 카피를 차례로 펼치는 읽기 보기를 비교한다. 새 페이지 링크나 다운로드를 추가하지 않는다. 사진 확대용 첫 클릭을 다시 만들지도 않는다.
- 기준: 자동·수동·정적 보기 간 내용이 빠지거나 중복 낭독되지 않는다. 읽기 보기에서 돌아오면 마지막 장면과 수동 정지 의도가 유지된다. [W3C Pause, Stop, Hide](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)

### C. 보던 내용과 선택을 이어가기

#### I15. 메뉴 닫기 뒤 초점과 위치를 예측 가능하게 — P1 / 코드 확인

- 현재: Esc 닫기는 메뉴 버튼으로 초점을 돌리고, 항목 선택은 제목으로 이동한다. 바깥 클릭·언어 패널 연동·폭 변경은 서로 다른 경로다.
- 제안: 항목을 선택한 경우에는 해당 제목, 탐색을 취소한 경우에는 메뉴 버튼이라는 정책을 정리한다. 일반 탐색 패널을 근거 없이 앱 메뉴나 모달로 바꾸지 않는다.
- 기준: 숨어 버린 링크에 초점이 남지 않고, 메뉴를 닫아도 원래 읽던 위치가 뜻하지 않게 위로 이동하지 않는다. [W3C Disclosure Navigation](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/examples/disclosure-navigation/)

#### I16. 현재 카테고리 표시 기준 정리 — P1 / 코드 확인·설계 제안

- 현재: nav에 연결된 섹션과 고정180px 기준으로 현재 항목을 찾는다. 사진 갤러리처럼 직접 메뉴 항목이 없는 구간에서는 앞 카테고리가 남는다.
- 제안: 각 섹션이 어느 카테고리에 속하는지 먼저 정하고, 실제 헤더 높이를 반영한다. 모든 섹션을 메뉴에 추가하는 것으로 해결하지 않는다.
- 기준: 메뉴의 선택 표시가 현재 읽는 내용과 이해 가능한 관계를 가진다. 메뉴에 없는 갤러리에서 지역별 별장이 표시된다는 사실만으로 오류를 단정하지 않는다.

#### I17. 뒤로가기에서 섹션 안의 읽기 위치 복원 — P1 / 관찰 확인·실기기 대기

- 현재: 모바일 `popstate`는 hash 섹션의 시작으로 이동한다. 390px 실제 개발 페이지에서 컨시어지 시설 설명을 읽다가 메뉴로 컨시어지 섹션 이동 후 뒤로가기를 누르면, 선택은 유지하지만 시설 섹션 y−675px가 y87px로 바뀌었다. 보던 설명 위치로 복귀하지 않았다.
- 제안: 사용자 카테고리 이동과 브라우저 복귀를 구분한다. 섹션 ID·섹션 내 상대 위치·선택 장면을 필요 범위에서 복원한다. BFCache 복귀에는 페이지 상태가 이미 남을 수 있으므로 중복 초기화하지 않는다.
- 기준: 뒤로가기를 여러 번 눌러야 탈출하는 사진별 기록을 만들지 않는다. 무조건 `scrollRestoration='manual'`로 바꾸기 전에 복원 구현을 검증한다. [MDN scrollRestoration](https://developer.mozilla.org/en-US/docs/Web/API/History/scrollRestoration), [web.dev bfcache](https://web.dev/articles/bfcache)

#### I18. 언어 전환에서 선택 유지 — P1 / 관찰 확인

- 현재: 실제 영문 언어 메뉴에서 한국어로 바꾸면 시설 섹션은 유지하지만 컨시어지 선택은 첫 시설로 초기화된다. 각 초기화 상태는 페이지 새 탐색의 결과다.
- 실제 사진 상태도 확인: 영문03/03·수동 정지에서 한국어01/03·정지 해제로 초기화됐다. 전환 후 사진 영역이 화면 밖이라 바로 넘겨지지는 않았다. 정지 의도 초기화와 즉시 자동 재생을 구분한다.
- 이어서 사진 영역으로 돌아왔을 때 자동 전환이 진행되는 것을 확인했다. 언어 변경 전에 선택한 정지 의도를 전달하는 보완이 필요하다.
- 제안: 같은 브라우저 세션에서 시설·사진·수동 정지·섹션 내 읽기 위치를 번역 화면에 전달한다. ID 기반으로 대응하며 번역된 문구 자체를 저장 키로 쓰지 않는다.
- 기준: 언어 변경 후 같은 내용을 읽고, 메뉴와 언어 패널은 닫힌다. 잘못된 저장 값은 안전한 첫 항목으로 복원한다. 세션 밖까지 남길 필요가 없는 상태는 영구 저장하지 않는다.

#### I19. 가로·세로 전환에서 읽기 기준점 유지 — P1 / 관찰 확인·실기기 대기

- 현재: 검토실390→844 크기 변경에서는 정지와 장면은 유지됐지만 갤러리가 화면 아래로 멀어졌다. 실제 폰 회전 결과와 구별한다.
- 제안: 회전 전 읽던 섹션과 장면을 기준으로 새 배치를 정한다. 사용자가 읽는 동안 이미지 로드·폰트 적용·주소창 변화로 위치가 바뀌는 것도 함께 확인한다.
- 기준: 방향을 잠그거나 세로로 돌리라는 차단 화면을 만들지 않는다. 확대 중 사용자의 화면 이동을 매 resize마다 강제로 되돌리지 않는다. [W3C Orientation](https://www.w3.org/WAI/WCAG22/Understanding/orientation.html), [MDN VisualViewport](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport)

#### I20. 시설 선택 결과가 가까이 보이도록 — P1 / 관찰 확인

- 현재: 390px 컨시어지 선택에서 사진은 가까이 있지만 제목 y822px로 화면 하단에 걸렸다. 이미지가 먼저 나오는 긴 패널과 3행 시설 선택 영역의 영향이다.
- 제안: 선택한 시설 이름을 탭 아래 가까이 보여주거나 설명과 사진의 순서를 비교한다. 탭을 누를 때마다 강제로 패널로 이동시키는 방식은 비교 탐색을 끊을 수 있어 기본으로 정하지 않는다.
- 기준: 클릭 후 한 번에 선택 성공을 이해한다. 사진 로드 중에도 현재 시설명이 보인다. 활성 탭은 색뿐 아니라 이름·선택 상태로 식별한다.

### D. 환경 변화와 느린 연결까지 고려하기

#### I21. 화면 폭과 입력 능력을 분리 — P1 / 코드 확인·실기기 대기

- 현재: 1023px 이하 터치에서만 밀기를 인식한다. 1024px 이상 터치 태블릿·터치 노트북은 제외된다. PC 마우스 드래그는 구현상 의도적으로 제외돼 있다.
- 추가 확인: 실제 페이지1024px 영문 헤더는 가로 넘침 없이 표시됐지만 일반 메뉴 링크 높이는 약20.8px였다.1023px에서는 메뉴 버튼 높이가50.4px였다. 넓은 터치 화면의 조작 편의는 별도로 확인한다. 링크 높이만으로 WCAG 실패를 단정하지 않는다.
- 제안: 레이아웃 분기는 폭으로 유지하되 조작 가능 여부는 터치·키보드·마우스 동시 사용을 고려한다. 태블릿에 마우스를 연결해도 터치를 없애지 않는다.
- 기준: 넓은 터치 화면에서도 같은 장면 선택 대안을 쓸 수 있다. `any-pointer`는 능력 힌트이지 모든 입력을 차단하는 기준이 아니다. 동시 입력 기준 2.5.6은 AAA다. AA 필수 기준으로 잘못 설명하지 않는다. [MDN any-pointer](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/any-pointer), [W3C Concurrent Input](https://www.w3.org/WAI/WCAG22/Understanding/concurrent-input-mechanisms.html)

#### I22. 다음 사진 준비와 설명의 일치 — P1 / 코드 확인·설계 제안

- 현재: 슬라이드 사진은 lazy 로딩을 사용하고 전환은 준비 여부를 기다리지 않는다. 이번 로컬 관찰에서 빈 이미지 오류는 확인하지 않았다.
- 제안: 현재와 바로 다음 장면만 필요한 시점에 준비한다. 사진이 준비되면 번호·설명과 함께 표시한다. 모든 큰 이미지를 처음부터 높은 우선순위로 받지 않는다.
- 기준: 빠르게 여러 번 선택할 때 늦게 완료된 이전 사진이 현재 캡션에 붙지 않는다. 요청 순서 ID를 확인하며 사진 준비가 끝나야 읽기 시간을 시작한다. [MDN decode](https://developer.mozilla.org/en-US/docs/Web/API/HTMLImageElement/decode), [web.dev image lazy loading](https://web.dev/articles/browser-level-image-lazy-loading)

#### I23. 사진 실패 시 선택과 설명을 남기고 복구 — P1 / 코드 확인·설계 제안

- 현재: 사진 덱에는 로드 실패 시의 재시도 UI가 없다. `complete`만으로 정상 로드를 판별할 수 없다. 실패한 이미지도 complete가 true일 수 있다.
- 제안: 준비·성공·실패 상태를 구분한다. 실패하면 제목과 설명은 남기고 현재 영역에서 재시도한다. 연속 실패 시 자동 전환을 계속 돌리지 않는다.
- 기준: 깨진 이미지 아이콘만 남지 않는다. 오프라인을 확실히 알 수 없는 경우 단정적인 네트워크 안내를 하지 않는다. 실패 복구 후 수동 정지를 해제하지 않는다. [MDN complete](https://developer.mozilla.org/en-US/docs/Web/API/HTMLImageElement/complete)

#### I24. 로고 전용 가로형 자산과 테마 규칙 — P1 / 코드 확인·실기기 대기

- 현재: 세로형 원본을 CSS로 심볼·워드마크로 나눠 잘라서 사용한다. 최근 점 형태 노출과 오른쪽 잘림은 crop·컨테이너 조정으로 보완했다.
- 유지: 밝은 로고 표면, `color-scheme:only light`, 이미지 filter·mix-blend 정리는 이미 적용돼 있다. 이를 누락된 처리로 분류하지 않는다.
- 제안: 헤더용 가로형·작은 화면용 워드마크를 별도 자산으로 준비하고, 하단은 원래 구성을 유지한다. 기존 브랜드 색과 텍스트를 보존하며 실제 강제 다크모드에서 대응 자산이 필요한지 확인한다.
- 기준: 화면 폭·font 로드·flex 수축과 무관하게 오른쪽이 잘리지 않는다. 흰색/검은색 배경에서 브랜드 형태가 보이고, 이미지 배경 사각형이나 반전된 글자가 생기지 않는다. CSS 검토 테마로 실기기 강제 다크모드 검수를 대체하지 않는다.
- 브라우저 참고: Samsung의2020년 기술 설명은 로고와 배경 변환의 한계를 다룬다. Chrome의2021년 Auto Dark 글은 당시 실험을 설명한다. 그 글의 설정 경로나 동작을2026년 모든 브라우저에 적용되는 보장으로 쓰지 않는다. 현재 CSS 문서와 실제 버전을 함께 확인한다. [Samsung Dark Mode](https://developer.samsung.com/browser/blog/en/2020/12/15/dark-mode-in-samsung-internet), [MDN color-scheme](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/color-scheme)

## 5. 재생과 복귀의 구체적인 정책안

### 5.1 중단 이유를 분리한다

`사용자가 정지함`, `메뉴가 열림`, `조작 초점이 있음`, `손가락 조작 중`, `화면 밖`, `문서 숨김`, `동작 줄이기`, `사진 준비 중/실패`를 독립된 이유로 관리한다. 메뉴를 닫을 때 하나의 이유만 해제하고, 사용자가 누른 정지까지 지우지 않는다.

| 상황 | 제안 동작 | 사용자 의도 보존 |
|---|---|---|
| 자동 재생 중 좌우 밀기 | 손이 닿으면 멈춤 → 성공한 장면 표시 → 읽기 시간 새로 부여 | 다음 장면을 즉시 볼 수 있음 |
| 수동 정지 중 좌우 밀기·장면명 선택 | 장면만 변경, 정지 유지 | 정지 상태 유지 |
| 메뉴·언어 패널 열기 | 해당 화면의 자동 재생 중단 | 읽던 장면 유지 |
| 패널 닫기 | 중단 이유를 다시 계산 | 수동 정지는 해제하지 않음 |
| 키보드 초점으로 조작 시작 | 자동 전환 중단 | 명시적 재생 선택 전 읽기 보장 |
| 화면 밖·앱 전환 | 재생 중단, 진행 중 제스처 정리 | 반환 직후 즉시 넘기지 않음 |
| 이미지 준비 안 됨 | 이전 장면 또는 준비 안내를 유지 | 현재 사진과 설명을 일치시킴 |
| 로드 실패 | 설명과 복구 수단 유지, 자동 전환 중단 | 반복 실패를 숨기지 않음 |
| 동작 줄이기 | 자동 전환 중단, 모든 장면 접근 대안 제공 | 정보는 동일하게 제공 |
| 언어 변경 | 대응하는 섹션·시설·장면과 정지 상태 복원 | 번역만 바뀌며 읽기 이어감 |

복귀 때 무조건 재생하거나 무조건 영구 정지하는 정책을 하나로 적용하지 않는다. 잠깐 가려진 경우와 사용자가 읽기 모드로 들어간 경우를 나눠야 한다. 코드에 중단 이유를 정리한 뒤 실제 입력에서 검수한다. [MDN Page Visibility](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API)

### 5.2 화면마다 조작을 새로 배우지 않게 한다

- 사진 갤러리·생활 슬라이드는 같은 밀기 방향, 번호 표현, 정지 이름, 장면명 선택 규칙을 사용한다.
- 시설 탭은 선택에 따른 내용 변경이며 자동 넘기기로 바꾸지 않는다. 2열 배치여도 실제 키보드 탭 패턴을 유지하고, 위·아래 키를 강제로 가로 탭 이동에 쓰지 않는다. [W3C APG Tabs](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/)
- 영상 음량과 재생은 서로 다른 버튼으로 유지한다. 사진을 넘기는 조작이 음량이나 외부 링크를 실행하지 않게 한다.
- 외부 치앙마이 이미지 링크는 클릭 한 번 연결이라는 사용자 결정을 유지한다. 새 이미지 확대 클릭 단계를 끼워 넣지 않는다.

### 5.3 조작 면적과 가독성

새 장면 선택 조작은 약48px 높이를 시안 기준으로 비교한다. 기존44px 버튼을 일괄 실패로 판정하지 않는다. WCAG 2.2 AA의 최소 대상 크기 기준은24×24 CSS px 또는 예외 조건이며,48px는 이 사이트의 여유 있는 설계 목표다. [W3C Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

활성 상태는 색만으로 전달하지 않고 선택 이름·테두리·문자와 프로그램 상태를 맞춘다. 네온 테두리는 조작 상태 표현과 혼동되지 않아야 한다. 고정 조작부를 도입한다면 키보드 초점이 헤더나 조작부에 완전히 가려지지 않게 한다. [W3C Focus Not Obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)

### 사용성 관찰 과제

실제 방문자 자료가 생기기 전에는 아래 과제를 대표 사용자에게 실행해 설계값을 조정한다.60–70대 참여자를 포함할 경우 본인의 평소 확대 설정을 사용한다. 연령만으로 모든 참여자의 읽기 능력을 단정하지 않는다.

1. 기다리지 않고 테라스 사진 찾아보기.
2. 장면을 정지하고 설명을 끝까지 읽기.
3. 사진의 세부를 확대해서 본 뒤 다음 사진으로 이동하기.
4. 시설 컨시어지를 고르고 설명이 바뀌었는지 확인하기.
5. 다른 카테고리를 본 뒤 뒤로가기로 보던 내용 이어 읽기.
6. 영문으로 바꾼 뒤 같은 시설·장면 찾기.

성공 여부, 잘못 누름, 자동 전환으로 읽기를 놓침, 복귀 후 위치 찾기, 조작 발견까지의 과정과 발언을 기록한다. 조사 없이 성공률·전환율·매출 개선 수치를 기획서에 넣지 않는다.
